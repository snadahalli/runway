# Runway — working notes

macOS menu bar app tracking Claude plan limits. Read `README.md` first for the
product concept and the accuracy reasoning; this file is the build/dev context.

## Build

```sh
./build.sh                              # app only, ad-hoc signed, no Apple account
DEVELOPMENT_TEAM=XXXXXXXXXX ./build.sh  # adds the WidgetKit extension
open .build/Build/Products/Release/Runway.app
```

`Runway.xcodeproj` is generated by xcodegen from `project.yml` and is
gitignored — never hand-edit it, edit the spec. `project-widget.yml` includes
the base spec and layers the widget target on top.

Adding a source file needs no spec change: targets reference whole directories
(`Sources/Shared`, `Sources/App`, `Sources/Widget`).

## Architecture

`AppModel` is the only engine. It publishes exactly one value, `RunwaySnapshot`,
and every surface — menu bar label, popover, widget — renders from it. The widget
reads the same struct off disk.

Two independent cadences:
- **API poll** every 180s (hard floor, see below), driven by `pollTask`
- **Local log scan** every 15s, driven by `scanTimer`, free and unlimited

Between API polls the snapshot is marked `.estimated` and each limit's percentage
is extrapolated from local token volume using the calibrated tokens-per-percent.
Clamped so it can never run backwards or exceed 100.

## Things that will bite you

- **`User-Agent: claude-code/<version>` is mandatory** on the usage endpoint.
  Without it you land in a much stricter rate-limit bucket and get persistent
  429s. Version is scraped from the `version` field in the transcript JSONL
  (`TranscriptScanner.detectCLIVersion`) rather than shelling out to `claude`.
- **Never poll faster than 180s.** `UsageAPIClient.minimumPollInterval` enforces
  it regardless of the settings value.
- **The 5-hour window rolls**, so its percentage falls as well as rises.
  `Projection.calibrate` ignores non-positive deltas for this reason.
- **Cache token pricing is the whole ballgame.** Cache reads are ~97% of tokens
  in real usage and cost 0.1× input. The 5m/1h write split comes from
  `usage.cache_creation.ephemeral_{5m,1h}_input_tokens`.
- **Ad-hoc signatures change every build**, so the keychain prompt reappears
  after each rebuild. Not a bug. A stable identity fixes it.
- `start()` is called from `RunwayApp.init`, **not** from a `.task` on the
  popover — otherwise nothing polls until the user opens the menu, and alarms
  never fire for someone who never clicks.

## Verified working (2026-07-31)

Built and ran against a live Max 5x account. Confirmed:
- usage endpoint returns 200 with the headers in `UsageAPIClient`
- three limits parsed: `session`, `weekly_all`, `weekly_scoped` (Fable)
- ledger over 7 days: ~$296 API-equivalent, attributed across 6 repos
- extrapolation between polls flips health `live` → `estimated` correctly

## Not done yet

- Widget is written and compiles into the spec but has **never been built or
  run** — needs `DEVELOPMENT_TEAM` set. Verify the App Group container actually
  resolves for the extension before trusting it.
- No app icon (`ASSETCATALOG_COMPILER_APPICON_NAME` is empty).
- No launch-at-login. `SMAppService.mainApp.register()` is the modern route.
- Alarm history is in-memory only; it clears on relaunch. `firedKeys` (the
  dedupe set) does persist in UserDefaults.
- `Pricing.swift` is a hand-maintained rate card. Sonnet 5 introductory pricing
  is deliberately not applied. Re-check when list prices move.
- No tests. `TranscriptScanner.parse` and `Projection.calibrate` are the two
  worth covering first — both are pure functions over fixture data.
